# MemeStorage

Хранилище мемов (картинки, видео, аудио) с поиском по текстовому запросу. Эмбеддинги считает `google/embeddinggemma-2`, векторы лежат в ChromaDB, файлы — локально. Доступ через gRPC, HTTP (FastAPI) и CLI-клиент.

## Требования

- Python 3.14+
- DLL FFmpeg — нужны `torchcodec` для видео

### FFmpeg

Проще всего скачать DLL в папку `ffmpeg` проекта, сервер подключит их сам:

```powershell
make ffmpeg
```

Без `make`:

```powershell
python fetch_ffmpeg.py
```

Скачивается LGPL shared-сборка FFmpeg 9 из [BtbN/FFmpeg-Builds](https://github.com/BtbN/FFmpeg-Builds), контрольная сумма архива проверяется. Повторный запуск заменяет содержимое папки.

Если папки `ffmpeg` нет, `torchcodec` ищет FFmpeg в `PATH`, тогда подойдёт и установленная shared-сборка:

```powershell
winget install Gyan.FFmpeg.Shared
```

## ONNX

`gemma.backend: onnx` запускает ту же модель через onnxruntime с int8-весами (`*_quantized`). Веса скачиваются при первом запуске в `$HF_HOME/onnx/embeddinggemma-2`, энкодеры картинок/видео и звука открываются только когда приходит файл такого типа. `device` должен быть `cpu`, `dtype` игнорируется, остальные ключи `gemma` работают так же.

Сравнение с `torch` (bfloat16) на файлах из `tests/videos`, картинках и звуке, 2 потока:

| | `torch` | `onnx` |
|---|---|---|
| Косинус векторов файлов | эталон | видео ≥ 0,998, картинки ≥ 0,999, аудио ≥ 0,994 |
| Косинус векторов запросов | эталон | ≥ 0,9999 |
| RSS на потоке видео | ~2,3 ГБ (пик 2,8) | ~1,1 ГБ (пик 2,0) |

## Конфигурация

Сервер читает `config.yaml` из текущей директории:

```yaml
app:
  save_strategy: "safe"

auth:
  admin_token: "замените-на-длинную-случайную-строку"

activity:
  retention_days: 90
  record_queries: true

gemma:
  device: "cuda"
  dtype: "bfloat16"
  semaphore_count: 4
  max_batch: 5

chroma:
  path: "./.runtime/storage.chromadb"

files:
  root: "./.runtime/files/"
  thumbnails_root: "./.runtime/thumbnails/"
  sqlite_connection_string: "./.runtime/sqlite.db"
  chunk_size: 65536

limits:
  max_image_mb: 20
  max_video_mb: 200
  max_audio_mb: 50
  max_video_seconds: 120
  max_audio_seconds: 300
  max_batch_files: 20
  max_queue: 100

thumbnails:
  size: 320
  quality: 85

grpc:
  port: "[::]:50051"
  max_workers: 4
  max_records: 32

http:
  host: "0.0.0.0"
  port: 8000
  max_workers: 4
```

|---|---|---|

| `auth.admin_token` | токен администратора, не короче 24 символов. Им создаются пользователи, см. [Авторизация](#авторизация-и-пользователи) | обязательный |
| `activity` | необязательная секция журнала событий, см. [Статистика и журнал](#статистика-и-журнал) | журнал включён |
| `activity.enabled` | писать ли журнал | `true` |
| `activity.retention_days` | сколько дней хранить события, старые удаляются | `90` |
| `activity.record_queries` | сохранять ли текст поисковых запросов (журнал и «топ запросов») | `true` |
| `gemma.device` | `cpu`, `cuda` (нужна CUDA-сборка PyTorch) | `cpu` |
| `gemma.backend` | `torch` — оригинальные веса; `onnx` — int8-версия из `onnx-community/embeddinggemma-2-ONNX`, только CPU, втрое меньше памяти на видео, см. [ONNX](#onnx) | `torch` |
| `gemma.dtype` | `float32`, `float16`, `bfloat16` | `float32` |
| `gemma.semaphore_count` | сколько вызовов модели выполняется одновременно, общий лимит для gRPC и HTTP | `4` |
| `gemma.max_batch` | сколько файлов или текстов модель обрабатывает за один проход | обязательный |
| `gemma.threads` | потоки PyTorch; желательно установить колличество ядер | на усмотрение torch |
| `gemma.truncate_dim` | `128`, `256`, `512`, `768` — Matryoshka-усечение эмбеддингов (с перенормировкой), меньше индекс и RAM; после смены нужна переиндексация | `768` |
| `gemma.idle_unload_seconds` | через сколько секунд простоя модель выгружается из памяти; следующий запрос загрузит её заново | не выгружать |
| `gemma.query_cache_size` | сколько текстов поисковых запросов держат готовый эмбеддинг в памяти; `0` выключает кэш | `256` |
| `chroma.path` | путь к базе ChromaDB | обязательный |
| `files.root` | директория для файлов | обязательный |
| `files.thumbnails_root` | директория для превью, см. [Превью](#превью) | обязательный |
| `files.sqlite_connection_string` | путь к файлу SQLite | обязательный |
| `files.chunk_size` | размер чанка в байтах при чтении файлов | `65536` |
| `limits` | необязательная секция, см. [Лимиты](#лимиты). Любой ключ можно пропустить или поставить `0`, это значит «без лимита» | без лимитов |
| `limits.max_image_mb`, `max_video_mb`, `max_audio_mb` | наибольший размер файла каждого типа, МБ | — |
| `limits.max_video_seconds`, `max_audio_seconds` | наибольшая длительность видео и аудио, секунды | — |
| `limits.max_batch_files` | сколько файлов принимает один пакетный запрос | — |
| `limits.max_queue` | сколько задач может ждать или выполняться в очереди одновременно | — |
| `thumbnails` | необязательная секция; без неё превью строятся с размерами по умолчанию | — |
| `thumbnails.size` | длина большей стороны превью в пикселях | `320` |
| `thumbnails.quality` | качество JPEG превью, `1..100` | `85` |
| `grpc` | необязательная секция; без неё gRPC не запускается | — |
| `grpc.port` | адрес `host:port` | обязательный |
| `grpc.max_workers` | число потоков gRPC-сервера | `4` |
| `grpc.max_records` | наибольший `record_count` в поисковых запросах gRPC | `32` |
| `http` | необязательная секция; без неё HTTP не запускается | — |
| `http.host` | адрес, на котором слушает HTTP-сервер | `127.0.0.1` |
| `http.port` | порт HTTP-сервера | `8000` |
| `http.max_workers` | число потоков для обработчиков HTTP-запросов | `4` |

Нужна хотя бы одна из секций `grpc` и `http`.

### Сохранение пачки

Сервер сохраняет пачку файлов по шагам: файлы пишутся на диск, для каждого сразу строится [превью](#превью), одним вызовом модели считаются эмбеддинги файлов, вторым — эмбеддинги описаний, записи одним вызовом добавляются в ChromaDB. Готовые эмбеддинги из запроса модель не пересчитывает, но их размерность проверяется до всех вызовов модели. Если файл не прошёл какой-то шаг, сервер удаляет его с диска и из векторной базы и сообщает об ошибке с этапом, на котором она случилась. Остальные файлы пачки сохраняются.

Когда модель или ChromaDB падают на всей пачке, поведение зависит от `app.save_strategy`:

- `safe` — сервер повторяет шаг для каждого файла по отдельности и отбрасывает только те, на которых шаг снова падает. Медленнее при ошибках, зато один битый файл не тянет за собой остальные.
- `fast` — сервер отбрасывает все файлы пачки, которые дошли до этого шага. Если упала модель, в сообщении об ошибке нет имени файла, только `batch failure on embedding` или `batch failure on description embedding`, по одному на каждый отброшенный файл.

Превью строится для каждого файла отдельно, поэтому `app.save_strategy` на этот шаг не влияет: файл, для которого превью не построилось, отбрасывается один, до вызовов модели.

Одиночная загрузка (`Save`, `POST /files`) работает так же, как пачка из одного файла.

### Превью

Превью строится сразу после записи файла на диск и лежит в `files.thumbnails_root` под именем `<id>.jpg`. Это JPEG, большая сторона которого не длиннее `thumbnails.size`:

- картинка поворачивается по EXIF, прозрачные места заливаются белым, маленькие картинки не увеличиваются;
- у анимированных GIF и WebP берётся первый кадр;
- у видео берётся кадр на середине длительности, а если длительности нет в заголовке файла (так бывает, например, у WebM, записанных браузером), — первый кадр. Видео декодирует `torchcodec`, поэтому для него нужен [FFmpeg](#ffmpeg).

Если файл не удаётся открыть, чтобы построить превью, файл не сохраняется: он удаляется с диска вместе с записью и попадает в ошибки с этапом `thumbnail`. Для клиента это его ошибка, а не сервера: HTTP `415`, gRPC `INVALID_ARGUMENT` (в пакетных запросах файл просто попадает в `failed`). При удалении файла из хранилища удаляется и его превью.

У аудио своего превью нет, на диск для него ничего не пишется. Вместо превью сервер отдаёт заглушку — серую картинку 320×320 с иконкой типа файла: нотой для аудио, картинкой для картинок, кнопкой «плей» для видео. Заглушку своего типа получают и картинки с видео, у которых превью на диске нет, например загруженные до появления превью. По ответу заглушку от превью не отличить: тот же `image/jpeg`.

#### Превью для старых файлов

Файлы, загруженные до появления превью, получают заглушки. Построить для них настоящие превью можно разовой командой:

```powershell
make thumbnails
```

Без `make`:

```powershell
python build_thumbnails.py
```

Скрипт читает тот же `config.yaml`, что и сервер, поэтому запускается из корня проекта, и может работать при запущенном сервере. Он проходит по всем файлам хранилища и строит превью тем же способом, что и сервер. Аудио и файлы, у которых превью уже есть, пропускаются, так что повторный запуск безопасен. Если превью для файла не строится, скрипт печатает id, имя файла и причину и идёт дальше; сам файл не удаляется. В конце печатается итог: сколько превью построено, сколько файлов пропущено и сколько с ошибкой.

### Лимиты

Размер файла проверяется, пока он пишется на диск: слишком большой файл обрывается и удаляется, а не доходит до модели. Длительность видео и аудио читается из сохранённого файла перед тем, как его берёт модель. Ответ на нарушение: HTTP `413`, gRPC `RESOURCE_EXHAUSTED`; в пакетных запросах такой файл попадает в `failed` с `kind` `limit_exceeded`, остальные файлы сохраняются. Файл сверх `max_batch_files` и сверх свободных мест в очереди тоже получает `limit_exceeded`. Файл, у которого не читается длительность, отклоняется с `embedding_model`.

Лимиты действуют на все пути загрузки: `POST /files`, `/files/batch`, `/jobs`, `/jobs/batch`, `Save`, `SaveMultiple`, `Submit`, `SubmitMultiple`. `max_queue` строгий: место в очереди занимается до чтения файла под общим замком, поэтому одновременные запросы не могут её превысить. Файл, который не прошёл лимиты, место возвращает.

### Асинхронная загрузка

Некоторые видео занимают десятки секунд, поэтому кроме `POST /files` есть загрузка через очередь: сервер сохраняет файл, сразу отвечает `202` с id задачи, а эмбеддинги считает фоновый поток. id задачи совпадает с id файла. Статус задачи: `pending`, `running`, `done` (файл находится поиском) или `failed` (файл удалён, в `error` причина). Очередь хранится в SQLite (`files.sqlite_connection_string`, таблица `jobs`) и переживает перезапуск: прерванная задача выполняется заново. Записи о завершённых задачах не удаляются.

Фоновый поток один, потому что модель всё равно считает по одному вызову. Готовые эмбеддинги в асинхронной загрузке принимаются так же, как в синхронной, и ждут в очереди вместе с файлом. Синхронные методы остаются как были.

### Готовые эмбеддинги

Готовый эмбеддинг попадает в индекс как есть, и неверный вектор поднимет файл в выдачу по чужим запросам. Поэтому `embeddings` и `text_embeddings` принимают только пользователи с правом `allow_embeddings` (его выдаёт админ) и сам админ. Остальным: HTTP `403`, gRPC `PERMISSION_DENIED`. В пакетных gRPC-вызовах (`SaveMultiple`, `SubmitMultiple`) такой файл попадает в `failed` с видом `FORBIDDEN`, остальные сохраняются. Размерность проверяется после права: `422` и `INVALID_ARGUMENT`.

## Авторизация и пользователи

Каждый запрос, кроме `GET /health`, должен нести токен: `Authorization: Bearer <токен>` в HTTP и метаданные `authorization: Bearer <токен>` в gRPC. Без токена или с чужим, отозванным или удалённым: HTTP `401`, gRPC `UNAUTHENTICATED`. Сервер не запускается без `auth.admin_token`.

- **Токен админа** лежит в конфиге. Он открывает админские методы и все обычные. Файлы, загруженные админом, не имеют владельца.
- **Токен пользователя** создаёт админ. Пользователь загружает, ищет и скачивает, но админские методы получают `403` и `PERMISSION_DENIED`.
- Токен показывается один раз при создании. В базе лежит только его SHA-256, украденная база токенов не раскрывает. Токен потерян: админ выпускает новый, старый перестаёт работать сразу.
- Удаление пользователя отзывает токен и оставляет пользователя в списке с пометкой. Его файлы и статистика остаются, имя занято навсегда. Вернуть такого пользователя можно выпуском нового токена: он снова активен со всеми прежними правами и файлами, а в ответе `restored` равен `true`. Пока токена нет, менять его настройки нельзя.
- Файлы получают владельца при загрузке (в том числе через очередь). У файлов, загруженных до появления пользователей, владельца нет, они показываются в статистике как «без владельца». База с файлами обновляется сама, миграция не нужна.

Токены ходят открытым текстом, а сервер сам TLS не терминирует. Закрывает это обратный прокси, например nginx: он держит сертификат, а сервер слушает только `127.0.0.1`. Чтобы мимо прокси не ходили, поставьте в конфиге `http.host: "127.0.0.1"` и `grpc.port: "127.0.0.1:50051"`.

Пример для nginx (не проверялся на этом проекте, проверьте на своих сертификатах и доменах):

```nginx
# HTTP API
server {
    listen 443 ssl;
    http2 on;
    server_name memes.example.com;
    ssl_certificate     /etc/letsencrypt/live/memes.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/memes.example.com/privkey.pem;

    # Не меньше самого большого limits.max_*_mb, иначе nginx отвергнет файл раньше сервера
    client_max_body_size 250m;
    # Файлы идут на сервер потоком, не копятся в nginx
    proxy_request_buffering off;
    # Видео считается десятки секунд внутри запроса
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# gRPC API
server {
    listen 50052 ssl;
    http2 on;
    server_name memes.example.com;
    ssl_certificate     /etc/letsencrypt/live/memes.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/memes.example.com/privkey.pem;

    client_max_body_size 0;
    grpc_read_timeout 600s;
    grpc_send_timeout 600s;

    location / {
        grpc_pass grpc://127.0.0.1:50051;
    }
}
```

Клиенту CLI тогда нужен флаг `--tls`: `python cli.py --tls --server memes.example.com:50052 ...`.

IP в журнале: для HTTP uvicorn берёт настоящий адрес из `X-Forwarded-For`, если прокси стоит на той же машине (по умолчанию он доверяет `127.0.0.1`). Для gRPC в журнале будет адрес прокси.

Сравнение токена админа идёт за постоянное время, токены нигде не пишутся в журнал.

Админские методы (HTTP `/admin/...` и одноимённые вызовы gRPC):

| HTTP | gRPC | Что делает |
|---|---|---|
| `POST /admin/users` | `CreateUser` | создать пользователя: `{"name", "allow_embeddings"}` → пользователь и токен |
| `GET /admin/users` | `ListUsers` | список, удалённые тоже |
| `PATCH /admin/users/{id}` | `UpdateUser` | изменить `allow_embeddings` |
| `DELETE /admin/users/{id}` | `DeleteUser` | отозвать токен |
| `POST /admin/users/{id}/token` | `RotateToken` | выпустить новый токен, удалённому пользователю тоже: он возвращается в строй |
| `GET /admin/stats` | `GetStats` | файлы и байты каждого пользователя по картинкам, видео и аудио |
| `GET /admin/activity/summary` | `GetActivity` | сводка журнала за период |
| `GET /admin/activity/events` | — | журнал событий с фильтрами |
| `GET /admin/files` | — | файлы с владельцем, размером и временем, страницами |
| `DELETE /admin/files/{id}` | — | удалить файл с диска и из индекса |

Время везде в секундах Unix. Для обычного `curl`:

```powershell
$h = @{ Authorization = "Bearer $env:ADMIN_TOKEN" }
Invoke-RestMethod -Method Post -Headers $h -ContentType application/json -Uri http://localhost:8000/admin/users -Body '{"name":"anna"}'
Invoke-RestMethod -Headers $h http://localhost:8000/admin/stats
```

## Статистика и журнал

Сервер ведёт две вещи.

**Статистика файлов** (`/admin/stats`, `GetStats`) считается по хранилищу: сколько файлов и байт у каждого пользователя, отдельно картинки, видео и аудио, и когда был последний аплоад. Удалённые файлы в ней не учитываются.

**Журнал событий** пишется на каждое действие: любой HTTP-запрос, любой вызов gRPC (в том числе отказанный и неопознанный), каждую завершённую фоновую задачу. В событии: время, кто (пользователь, `admin`, `worker` или никто), что (имя обработчика), чем кончилось (код и один из четырёх исходов `ok`, `denied`, `client_error`, `server_error`), сколько заняло, сколько байт пришло и ушло, IP, путь без query-строки и для поиска текст запроса. `/health` не пишется. Токены не пишутся никогда.

Событие кладётся в очередь и пишется отдельным потоком пачками, поэтому журнал не замедляет запросы и не роняет их. Если запись не успевает, лишние события отбрасываются, а их число видно в сводке (`dropped`).

Сводка (`/admin/activity/summary?since=&until=`, по умолчанию последние 7 дней) отдаёт: запросы по исходам, среднее время, трафик, разбивку по транспорту, действиям (число, ошибки, среднее, p95 и максимум времени, трафик), пользователям, дням и IP, десять с лишним самых частых поисковых запросов и состояние фоновых задач с причинами отказов. Отказы по IP удобно смотреть на подбор токенов.

IP HTTP-запроса берётся из адреса соединения с учётом `X-Forwarded-For` от доверенного прокси, IP вызова gRPC за прокси будет адресом прокси.

Текст запросов можно не сохранять: `activity.record_queries: false`. Журнал выключается через `activity.enabled: false`.

## Запуск сервера

```powershell
python main.py
```

При первом запуске скачивается модель. Если в конфиге есть обе секции, gRPC и HTTP работают в одном процессе с общей моделью. Ctrl+C останавливает оба сервера.

## HTTP API

Спецификация лежит в [`api/http/openapi.yaml`](api/http/openapi.yaml). Запущенный сервер отдаёт её же по адресу `/openapi.json`, а Swagger UI — по адресу `/docs`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/files` | загрузить файл (`multipart/form-data`) → `204` без тела |
| `POST` | `/files/batch` | загрузить несколько файлов (`multipart/form-data`) → `200 {"failed": [{"kind": ..., "message": ...}]}` |
| `POST` | `/jobs` | загрузить файл в очередь → `202 {"id": ...}`, см. [Асинхронная загрузка](#асинхронная-загрузка) |
| `POST` | `/jobs/batch` | загрузить несколько файлов в очередь → `202 {"jobs": [{"id": ..., "filename": ...}], "failed": [...]}` |
| `GET` | `/jobs/{id}` | статус задачи: `{"id", "original_name", "status", "error"}` |
| `GET` | `/files/{id}` | скачать файл; `?download=true` — отдать как вложение |
| `GET` | `/files/{id}/info` | имя и тип файла |
| `GET` | `/files/{id}/thumbnail` | превью файла (`image/jpeg`), см. [Превью](#превью) |
| `GET` | `/search?q=...&count=10` | поиск по одному запросу |
| `POST` | `/search/query` | поиск по нескольким запросам: `{"queries": [...], "count": 10}` |
| `POST` | `/search/embeddings` | поиск по готовым эмбеддингам: `{"embeddings": [[...]], "count": 10}` |
| `GET` | `/health` | проверка, что сервер жив (единственный маршрут без токена) |
| — | `/admin/...` | админские методы, см. [Авторизация](#авторизация-и-пользователи) |

Поля формы `POST /files`:

- `file` — обязательное, картинка, видео или аудио. Если тип не передан или равен `application/octet-stream`, сервер определяет его по имени файла. На другие типы сервер отвечает `415`.
- `description` — текстовое описание, файл находится и по нему.
- `embeddings` и `text_embeddings` — готовые эмбеддинги файла и описания в виде JSON-массива чисел. Размерность обоих должна совпадать с моделью сервера, иначе `422`.

`POST /files` и `POST /jobs` принимают `embeddings` и `text_embeddings` только от пользователей с правом, см. [Готовые эмбеддинги](#готовые-эмбеддинги).

`POST /files` не возвращает ничего при успешном сохранении. Если файл не удалось сохранить на одном из шагов, сервер отвечает `500`, в `detail` — этап и причина, например `Embedding model: error on embedding: cat.png`. Ничего не сохраняется.

`POST /files/batch` принимает файлы в повторяющемся поле `files`. Тип каждого файла определяется так же, как в `POST /files`. Описания и готовые эмбеддинги здесь не передаются. Файл, который не удалось сохранить, не роняет запрос: он попадает в `failed`, остальные файлы сохраняются. id сохранённых файлов не возвращаются.

Элемент `failed`:

- `kind` — этап, на котором файл отброшен: `unsupported_type` (не картинка, не видео и не аудио, до приложения файл не доходит), `file_storage`, `thumbnail` (файл не открылся, превью не построено), `embedding_model`, `vector_storage`, `limit_exceeded` (см. [Лимиты](#лимиты)).
- `message` — текст ошибки. Обычно в нём есть имя файла, но не всегда, см. [Сохранение пачки](#сохранение-пачки).

Ошибки возвращаются в виде `{"detail": ...}`:

| Код | Когда |
|---|---|
| `400` | у части формы с файлом нет имени |
| `401` | нет токена, токен неверный, отозван или удалён |
| `403` | готовые эмбеддинги от пользователя без права (`POST /files`, `POST /jobs`); админский метод с токеном пользователя |
| `404` | файла или задачи с таким id нет |
| `413` | файл больше или длиннее лимита (`POST /files`, `POST /jobs`) |
| `415` | файл не картинка, не видео и не аудио, или не декодируется: битый либо не то, что говорит его тип, превью не построить (`POST /files`, `POST /jobs`) |
| `429` | очередь заполнена (`POST /jobs`) |
| `422` | запрос не прошёл валидацию: битый uuid, `count` вне `1..100`, размерность эмбеддинга не совпадает с моделью и т. п. |
| `500` | файл не удалось сохранить из-за сбоя сервера: файловое хранилище, модель, векторная база (`POST /files`, `POST /jobs`) |

Для `422` поле `detail` — список ошибок по полям в формате FastAPI, для остальных кодов — строка.

```powershell
# Загрузить файл с описанием
curl.exe -F "file=@cat.png" -F "description=грустный кот" http://localhost:8000/files

# Загрузить несколько файлов одним запросом
curl.exe -F "files=@cat.png" -F "files=@dog.mp4" -F "files=@meow.mp3" http://localhost:8000/files/batch

# Найти 5 файлов по запросу
curl.exe -G http://localhost:8000/search --data-urlencode "q=грустный кот" -d count=5

# Скачать файл
curl.exe -o cat.png http://localhost:8000/files/<uuid>
```

После изменения HTTP API спецификацию нужно сгенерировать заново:

```powershell
make openapi
```

Без `make` (gRPC-код должен быть уже сгенерирован):

```powershell
python -m api.http.openapi
```

## gRPC API

Контракт лежит в [`api/grpc/proto/service.proto`](api/grpc/proto/service.proto).

| Метод | Что делает |
|---|---|
| `Save` | загрузить файл: поток из `info`, затем чанков `data` → пустой ответ |
| `SaveMultiple` | загрузить несколько файлов одним потоком → `failed` |
| `Submit` | загрузить файл в очередь → uuid задачи, см. [Асинхронная загрузка](#асинхронная-загрузка) |
| `SubmitMultiple` | загрузить несколько файлов в очередь → `jobs` (uuid и имя) и `failed` |
| `GetJob` | статус задачи: `PENDING`, `RUNNING`, `DONE`, `FAILED` и `error` |
| `GetFile` | скачать файл: поток из `info`, затем чанков `chunk` |
| `GetThumbnail` | превью файла одним ответом: `content_type` (`image/jpeg`) и байты `data`, то же, что `GET /files/{id}/thumbnail`, см. [Превью](#превью) |
| `GetByQuery` | поиск по текстовым запросам |
| `GetByEmbeddings` | поиск по готовым эмбеддингам |

`Save` возвращает пустой ответ, если файл сохранен успешно. Если файл не удалось сохранить на одном из шагов, вызов завершается с `INTERNAL`, ничего не сохраняется.

В `SaveMultiple` каждое сообщение `info` начинает новый файл, следующие за ним `data` — его содержимое. `info` — тот же `SaveFileInfo`, что и в `Save`: для каждого файла можно передать описание и готовые эмбеддинги. Эмбеддинги считаются после того, как сохранён весь поток. Файл, который не удалось сохранить, не роняет вызов: он попадает в `failed`, остальные файлы сохраняются. uuid сохранённых файлов не возвращаются.

Элемент `failed` — `SaveFailure` с полями `kind` (`UNSUPPORTED_TYPE`, `FILE_STORAGE`, `THUMBNAIL`, `EMBEDDING_MODEL`, `VECTOR_STORAGE`, `LIMIT_EXCEEDED`, `FORBIDDEN`) и `message`, значения те же, что у `failed` в [HTTP API](#http-api). Неверная размерность эмбеддинга в `SaveMultiple` тоже попадает в `failed` (`EMBEDDING_MODEL`), а не завершает вызов ошибкой.

Ошибки приходят как статусы gRPC, текст ошибки — в `details`:

| Статус | Когда |
|---|---|
| `INVALID_ARGUMENT` | первое сообщение `Save` или `SaveMultiple` не `info`; в `Save` следующее сообщение не `data`; неподдерживаемый тип файла или тип не определяется по имени (`Save`); размерность `embeddings` или `text_embeddings` не совпадает с моделью (`Save`, поиск); битый uuid; пустой список запросов или эмбеддингов; `record_count` меньше 1 или больше `grpc.max_records` |
| `NOT_FOUND` | файла с таким uuid нет (`GetFile`, `GetThumbnail`), задачи с таким uuid нет (`GetJob`) |
| `UNAUTHENTICATED` | нет токена в метаданных `authorization`, токен неверный, отозван или удалён |
| `PERMISSION_DENIED` | готовые эмбеддинги от пользователя без права (`Save`, `Submit`); админский вызов с токеном пользователя |
| `ALREADY_EXISTS` | имя пользователя занято, в том числе удалённым (`CreateUser`) |
| `UNAVAILABLE` | журнал событий выключен (`GetActivity`) |
| `RESOURCE_EXHAUSTED` | файл больше или длиннее лимита (`Save`, `Submit`); очередь заполнена (`Submit`) |
| `INVALID_ARGUMENT` | ещё: файл не декодируется, превью не построить (`Save`, `Submit`) |
| `INTERNAL` | файл не удалось сохранить из-за сбоя сервера (`Save`); поиск нашёл записи, файлов которых нет в хранилище (хранилища рассинхронизированы) |

## CLI-клиент

Клиенту нужен токен: переменная `MEMESTORAGE_TOKEN` (лучше) или `--token`. Аргументы командной строки видны другим пользователям машины.

```powershell
$env:MEMESTORAGE_TOKEN = "mst_..."
```

```powershell
# Загрузить файл или папку (-r — рекурсивно, -b — файлов в одном вызове, -j — число параллельных вызовов)
python cli.py upload ./memes -r -b 32 -j 4

# Загрузить с описанием (-d) для каждого файла
python cli.py upload ./memes -r -d "кот"

# Найти по запросу и скачать 5 лучших
python cli.py get "грустный кот" -o ./out -n 5

# Скачать по id
python cli.py download <uuid> <uuid> -o ./out
```

Админские команды, нужен токен админа:

```powershell
# Создать пользователя (--embeddings разрешает готовые эмбеддинги), токен печатается один раз
python cli.py user create anna

python cli.py user list
python cli.py user set anna --embeddings        # или --no-embeddings
python cli.py user token anna                   # новый токен, старый перестаёт работать; удалённого вернёт в строй
python cli.py user delete anna                  # отозвать токен, файлы остаются

# Кто что загрузил и что происходило на сервере за 7 дней
python cli.py stats --days 7
```

Пользователя в командах можно называть именем или id.

`upload` отправляет файлы пачками через `SaveMultiple`, по умолчанию по 32 файла (`-b`), описание из `-d` уходит вместе с каждым файлом. Файлы, тип которых не определяется как картинка, видео или аудио, клиент пропускает и не отправляет. Сервер не возвращает uuid, поэтому клиент выводит только пути файлов:

- `OK` — пачка сохранилась целиком, файл сохранён.
- `FAIL  <kind>: <message>` — ошибка от сервера по одному из файлов пачки.
- `PART` — файл из пачки, в которой не сохранилась часть файлов. Сервер не всегда называет файл в ошибке, поэтому клиент не знает, сохранён ли именно этот.
- `FAIL  <путь>` — файл из пачки, в которой не сохранился ни один файл или вызов завершился ошибкой.

В итоговой строке `Uploaded` и `failed` посчитаны по числу ошибок, которые вернул сервер.

Если хотя бы один id в `download` не является uuid, клиент ничего не скачивает и выводит список неправильных id.

Другой адрес сервера: `python cli.py --server host:50051 ...`
