# MemeStorage

Хранилище мемов (картинки, видео, аудио) с поиском по текстовому запросу. Эмбеддинги считает `google/embeddinggemma-2`, векторы лежат в ChromaDB, файлы — локально. Доступ через gRPC, HTTP (FastAPI) и CLI-клиент.

## Требования

- Python 3.14+
- DLL FFmpeg — нужны `torchcodec` для видео

### FFmpeg

Проще всего скачать DLL в папку `ffmpeg` проекта, сервер подключит их сам:

```powershell
make ffmpeg
```

Без `make`:

```powershell
python fetch_ffmpeg.py
```

Скачивается LGPL shared-сборка FFmpeg 9 из [BtbN/FFmpeg-Builds](https://github.com/BtbN/FFmpeg-Builds), контрольная сумма архива проверяется. Повторный запуск заменяет содержимое папки.

Если папки `ffmpeg` нет, `torchcodec` ищет FFmpeg в `PATH`, тогда подойдёт и установленная shared-сборка:

```powershell
winget install Gyan.FFmpeg.Shared
```

## Конфигурация

Сервер читает `config.yaml` из текущей директории:

```yaml
app:
  save_strategy: "safe"

gemma:
  device: "cuda"
  dtype: "bfloat16"
  semaphore_count: 4
  max_batch: 5

chroma:
  path: "./.runtime/storage.chromadb"

files:
  root: "./.runtime/files/"
  thumbnails_root: "./.runtime/thumbnails/"
  sqlite_connection_string: "./.runtime/sqlite.db"
  chunk_size: 65536

thumbnails:
  size: 320
  quality: 85

grpc:
  port: "[::]:50051"
  max_workers: 4
  max_records: 32

http:
  host: "0.0.0.0"
  port: 8000
  max_workers: 4
```

| Ключ | Значения | По умолчанию |
|---|---|---|
| `app.save_strategy` | `safe`, `fast` — что делать, когда модель или векторная база падают на пачке файлов, см. [Сохранение пачки](#сохранение-пачки) | обязательный |
| `gemma.device` | `cpu`, `cuda` (нужна CUDA-сборка PyTorch) | `cpu` |
| `gemma.dtype` | `float32`, `float16`, `bfloat16` | `float32` |
| `gemma.semaphore_count` | сколько вызовов модели выполняется одновременно, общий лимит для gRPC и HTTP | `4` |
| `gemma.max_batch` | сколько файлов или текстов модель обрабатывает за один проход | обязательный |
| `gemma.threads` | потоки PyTorch; желательно установить колличество ядер | на усмотрение torch |
| `gemma.truncate_dim` | `128`, `256`, `512`, `768` — Matryoshka-усечение эмбеддингов (с перенормировкой), меньше индекс и RAM; после смены нужна переиндексация | `768` |
| `gemma.idle_unload_seconds` | через сколько секунд простоя модель выгружается из памяти; следующий запрос загрузит её заново | не выгружать |
| `gemma.query_cache_size` | сколько текстов поисковых запросов держат готовый эмбеддинг в памяти; `0` выключает кэш | `256` |
| `chroma.path` | путь к базе ChromaDB | обязательный |
| `files.root` | директория для файлов | обязательный |
| `files.thumbnails_root` | директория для превью, см. [Превью](#превью) | обязательный |
| `files.sqlite_connection_string` | путь к файлу SQLite | обязательный |
| `files.chunk_size` | размер чанка в байтах при чтении файлов | `65536` |
| `thumbnails` | необязательная секция; без неё превью строятся с размерами по умолчанию | — |
| `thumbnails.size` | длина большей стороны превью в пикселях | `320` |
| `thumbnails.quality` | качество JPEG превью, `1..100` | `85` |
| `grpc` | необязательная секция; без неё gRPC не запускается | — |
| `grpc.port` | адрес `host:port` | обязательный |
| `grpc.max_workers` | число потоков gRPC-сервера | `4` |
| `grpc.max_records` | наибольший `record_count` в поисковых запросах gRPC | `32` |
| `http` | необязательная секция; без неё HTTP не запускается | — |
| `http.host` | адрес, на котором слушает HTTP-сервер | `127.0.0.1` |
| `http.port` | порт HTTP-сервера | `8000` |
| `http.max_workers` | число потоков для обработчиков HTTP-запросов | `4` |

Нужна хотя бы одна из секций `grpc` и `http`.

### Сохранение пачки

Сервер сохраняет пачку файлов по шагам: файлы пишутся на диск, для каждого сразу строится [превью](#превью), одним вызовом модели считаются эмбеддинги файлов, вторым — эмбеддинги описаний, записи одним вызовом добавляются в ChromaDB. Готовые эмбеддинги из запроса модель не пересчитывает, но их размерность проверяется до всех вызовов модели. Если файл не прошёл какой-то шаг, сервер удаляет его с диска и из векторной базы и сообщает об ошибке с этапом, на котором она случилась. Остальные файлы пачки сохраняются.

Когда модель или ChromaDB падают на всей пачке, поведение зависит от `app.save_strategy`:

- `safe` — сервер повторяет шаг для каждого файла по отдельности и отбрасывает только те, на которых шаг снова падает. Медленнее при ошибках, зато один битый файл не тянет за собой остальные.
- `fast` — сервер отбрасывает все файлы пачки, которые дошли до этого шага. Если упала модель, в сообщении об ошибке нет имени файла, только `batch failure on embedding` или `batch failure on description embedding`, по одному на каждый отброшенный файл.

Превью строится для каждого файла отдельно, поэтому `app.save_strategy` на этот шаг не влияет: файл, для которого превью не построилось, отбрасывается один, до вызовов модели.

Одиночная загрузка (`Save`, `POST /files`) работает так же, как пачка из одного файла.

### Превью

Превью строится сразу после записи файла на диск и лежит в `files.thumbnails_root` под именем `<id>.jpg`. Это JPEG, большая сторона которого не длиннее `thumbnails.size`:

- картинка поворачивается по EXIF, прозрачные места заливаются белым, маленькие картинки не увеличиваются;
- у анимированных GIF и WebP берётся первый кадр;
- у видео берётся кадр на середине длительности, а если длительности нет в заголовке файла (так бывает, например, у WebM, записанных браузером), — первый кадр. Видео декодирует `torchcodec`, поэтому для него нужен [FFmpeg](#ffmpeg).

Если файл не удаётся открыть, чтобы построить превью, файл не сохраняется: он удаляется с диска вместе с записью и попадает в ошибки с этапом `thumbnail`. При удалении файла из хранилища удаляется и его превью.

У аудио своего превью нет, на диск для него ничего не пишется. Вместо превью сервер отдаёт заглушку — серую картинку 320×320 с иконкой типа файла: нотой для аудио, картинкой для картинок, кнопкой «плей» для видео. Заглушку своего типа получают и картинки с видео, у которых превью на диске нет, например загруженные до появления превью. По ответу заглушку от превью не отличить: тот же `image/jpeg`.

#### Превью для старых файлов

Файлы, загруженные до появления превью, получают заглушки. Построить для них настоящие превью можно разовой командой:

```powershell
make thumbnails
```

Без `make`:

```powershell
python build_thumbnails.py
```

Скрипт читает тот же `config.yaml`, что и сервер, поэтому запускается из корня проекта, и может работать при запущенном сервере. Он проходит по всем файлам хранилища и строит превью тем же способом, что и сервер. Аудио и файлы, у которых превью уже есть, пропускаются, так что повторный запуск безопасен. Если превью для файла не строится, скрипт печатает id, имя файла и причину и идёт дальше; сам файл не удаляется. В конце печатается итог: сколько превью построено, сколько файлов пропущено и сколько с ошибкой.

## Запуск сервера

```powershell
python main.py
```

При первом запуске скачивается модель. Если в конфиге есть обе секции, gRPC и HTTP работают в одном процессе с общей моделью. Ctrl+C останавливает оба сервера.

## HTTP API

Спецификация лежит в [`api/http/openapi.yaml`](api/http/openapi.yaml). Запущенный сервер отдаёт её же по адресу `/openapi.json`, а Swagger UI — по адресу `/docs`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/files` | загрузить файл (`multipart/form-data`) → `204` без тела |
| `POST` | `/files/batch` | загрузить несколько файлов (`multipart/form-data`) → `200 {"failed": [{"kind": ..., "message": ...}]}` |
| `GET` | `/files/{id}` | скачать файл; `?download=true` — отдать как вложение |
| `GET` | `/files/{id}/info` | имя и тип файла |
| `GET` | `/files/{id}/thumbnail` | превью файла (`image/jpeg`), см. [Превью](#превью) |
| `GET` | `/search?q=...&count=10` | поиск по одному запросу |
| `POST` | `/search/query` | поиск по нескольким запросам: `{"queries": [...], "count": 10}` |
| `POST` | `/search/embeddings` | поиск по готовым эмбеддингам: `{"embeddings": [[...]], "count": 10}` |
| `GET` | `/health` | проверка, что сервер жив |

Поля формы `POST /files`:

- `file` — обязательное, картинка, видео или аудио. Если тип не передан или равен `application/octet-stream`, сервер определяет его по имени файла. На другие типы сервер отвечает `415`.
- `description` — текстовое описание, файл находится и по нему.
- `embeddings` и `text_embeddings` — готовые эмбеддинги файла и описания в виде JSON-массива чисел. Размерность обоих должна совпадать с моделью сервера, иначе `422`.

`POST /files` не возвращает ничего при успешном сохранении. Если файл не удалось сохранить на одном из шагов, сервер отвечает `500`, в `detail` — этап и причина, например `Embedding model: error on embedding: cat.png`. Ничего не сохраняется.

`POST /files/batch` принимает файлы в повторяющемся поле `files`. Тип каждого файла определяется так же, как в `POST /files`. Описания и готовые эмбеддинги здесь не передаются. Файл, который не удалось сохранить, не роняет запрос: он попадает в `failed`, остальные файлы сохраняются. id сохранённых файлов не возвращаются.

Элемент `failed`:

- `kind` — этап, на котором файл отброшен: `unsupported_type` (не картинка, не видео и не аудио, до приложения файл не доходит), `file_storage`, `thumbnail` (файл не открылся, превью не построено), `embedding_model`, `vector_storage`.
- `message` — текст ошибки. Обычно в нём есть имя файла, но не всегда, см. [Сохранение пачки](#сохранение-пачки).

Ошибки возвращаются в виде `{"detail": ...}`:

| Код | Когда |
|---|---|
| `400` | у части формы с файлом нет имени |
| `404` | файла с таким id нет |
| `415` | файл не картинка, не видео и не аудио (`POST /files`) |
| `422` | запрос не прошёл валидацию: битый uuid, `count` вне `1..100`, размерность эмбеддинга не совпадает с моделью и т. п. |
| `500` | файл не удалось сохранить (`POST /files`) |

Для `422` поле `detail` — список ошибок по полям в формате FastAPI, для остальных кодов — строка.

```powershell
# Загрузить файл с описанием
curl.exe -F "file=@cat.png" -F "description=грустный кот" http://localhost:8000/files

# Загрузить несколько файлов одним запросом
curl.exe -F "files=@cat.png" -F "files=@dog.mp4" -F "files=@meow.mp3" http://localhost:8000/files/batch

# Найти 5 файлов по запросу
curl.exe -G http://localhost:8000/search --data-urlencode "q=грустный кот" -d count=5

# Скачать файл
curl.exe -o cat.png http://localhost:8000/files/<uuid>
```

После изменения HTTP API спецификацию нужно сгенерировать заново:

```powershell
make openapi
```

Без `make` (gRPC-код должен быть уже сгенерирован):

```powershell
python -m api.http.openapi
```

## gRPC API

Контракт лежит в [`api/grpc/proto/service.proto`](api/grpc/proto/service.proto).

| Метод | Что делает |
|---|---|
| `Save` | загрузить файл: поток из `info`, затем чанков `data` → пустой ответ |
| `SaveMultiple` | загрузить несколько файлов одним потоком → `failed` |
| `GetFile` | скачать файл: поток из `info`, затем чанков `chunk` |
| `GetThumbnail` | превью файла одним ответом: `content_type` (`image/jpeg`) и байты `data`, то же, что `GET /files/{id}/thumbnail`, см. [Превью](#превью) |
| `GetByQuery` | поиск по текстовым запросам |
| `GetByEmbeddings` | поиск по готовым эмбеддингам |

`Save` возвращает пустой ответ, если файл сохранен успешно. Если файл не удалось сохранить на одном из шагов, вызов завершается с `INTERNAL`, ничего не сохраняется.

В `SaveMultiple` каждое сообщение `info` начинает новый файл, следующие за ним `data` — его содержимое. `info` — тот же `SaveFileInfo`, что и в `Save`: для каждого файла можно передать описание и готовые эмбеддинги. Эмбеддинги считаются после того, как сохранён весь поток. Файл, который не удалось сохранить, не роняет вызов: он попадает в `failed`, остальные файлы сохраняются. uuid сохранённых файлов не возвращаются.

Элемент `failed` — `SaveFailure` с полями `kind` (`UNSUPPORTED_TYPE`, `FILE_STORAGE`, `THUMBNAIL`, `EMBEDDING_MODEL`, `VECTOR_STORAGE`) и `message`, значения те же, что у `failed` в [HTTP API](#http-api). Неверная размерность эмбеддинга в `SaveMultiple` тоже попадает в `failed` (`EMBEDDING_MODEL`), а не завершает вызов ошибкой.

Ошибки приходят как статусы gRPC, текст ошибки — в `details`:

| Статус | Когда |
|---|---|
| `INVALID_ARGUMENT` | первое сообщение `Save` или `SaveMultiple` не `info`; в `Save` следующее сообщение не `data`; неподдерживаемый тип файла или тип не определяется по имени (`Save`); размерность `embeddings` или `text_embeddings` не совпадает с моделью (`Save`, поиск); битый uuid; пустой список запросов или эмбеддингов; `record_count` меньше 1 или больше `grpc.max_records` |
| `NOT_FOUND` | файла с таким uuid нет (`GetFile`, `GetThumbnail`) |
| `INTERNAL` | файл не удалось сохранить (`Save`); поиск нашёл записи, файлов которых нет в хранилище (хранилища рассинхронизированы) |

## CLI-клиент

```powershell
# Загрузить файл или папку (-r — рекурсивно, -b — файлов в одном вызове, -j — число параллельных вызовов)
python cli.py upload ./memes -r -b 32 -j 4

# Загрузить с описанием (-d) для каждого файла
python cli.py upload ./memes -r -d "кот"

# Найти по запросу и скачать 5 лучших
python cli.py get "грустный кот" -o ./out -n 5

# Скачать по id
python cli.py download <uuid> <uuid> -o ./out
```

`upload` отправляет файлы пачками через `SaveMultiple`, по умолчанию по 32 файла (`-b`), описание из `-d` уходит вместе с каждым файлом. Файлы, тип которых не определяется как картинка, видео или аудио, клиент пропускает и не отправляет. Сервер не возвращает uuid, поэтому клиент выводит только пути файлов:

- `OK` — пачка сохранилась целиком, файл сохранён.
- `FAIL  <kind>: <message>` — ошибка от сервера по одному из файлов пачки.
- `PART` — файл из пачки, в которой не сохранилась часть файлов. Сервер не всегда называет файл в ошибке, поэтому клиент не знает, сохранён ли именно этот.
- `FAIL  <путь>` — файл из пачки, в которой не сохранился ни один файл или вызов завершился ошибкой.

В итоговой строке `Uploaded` и `failed` посчитаны по числу ошибок, которые вернул сервер.

Если хотя бы один id в `download` не является uuid, клиент ничего не скачивает и выводит список неправильных id.

Другой адрес сервера: `python cli.py --server host:50051 ...`
